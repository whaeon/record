# 04 · 编码与协作约定

> 最后更新：2026-11-16 ｜ 本文件是规则与流程的唯一来源。

## 编码规范
- 后端分层：handler / service / repository
- 前端目录：src/pages, src/components, src/api
- 不写单元测试，任务内以本地 curl / 页面手动验证为准
- 全站界面文案统一使用「交易策略」，禁止残留「板块」；代码标识符禁止残留 sector
- 命名、目录结构变更属于约定变更，需在本文件更新并在 changelog 记录

## 任务执行规则（AI 必读）
1. 读 05 的「概览」表，取最上面一行未完成且非 PAUSED 的任务。
2. 只读该任务 ID 对应的「任务简报」块，**不读其他任务的简报**，不把其他任务的约束套用过来。
3. 按简报执行，逐条自检验收标准，汇报结果。
4. **完成后立即停止，不要自动开始下一个任务。**
5. 执行中的冲突按本文「执行中冲突处理」分类行动；只有该节「必须停止」的情形才停下来等人工。
6. 不得自行修改 05 中其他任务的简报，不得自行调整任务顺序。
7. 人工回复「T-XX 验收通过」时若同时要求不开始下一任务，只做清理，不启动下一任务。

## 执行中冲突处理

先分类，再行动。目标是把「该停的停、能继续的继续」写死，避免一律停工，也避免悄悄越权。

### A. 任务目标就是改锁定项

- **判定**：简报「目标」明确要求更换 01 技术栈、修改 02 已确认字段语义、或修改 03 已实现接口。
- **行动**：本任务简报即授权。按简报改代码，并在同一任务内同步对应锁定文档。即使「范围边界」漏列该文档，仍同步文档。changelog 写明理由。
- **越权边界**：目标未覆盖的锁定项保持不动。例如目标是迁 PostgreSQL，接口路径仍按 03 已实现契约保持。

### B. 范围边界漏列、但验收必需的配套文件

- **判定**：文件既不在「允许修改」也不在「禁止修改」；不做就无法满足验收标准。典型：`go.mod` / `main.go` 接线、Compose 配套 Dockerfile / nginx、`.gitignore` 产物目录、简报点名的迁移脚本。
- **行动**：可以改，自检汇报里列出「范围外但必需」的文件。
- **禁止修改列表中的文件一律不改。** 若某条验收标准实际上要求改禁止项：属于简报自相矛盾，停止汇报，等人工改简报。

### C. 环境或工具的字面步骤失败，验收标准仍可达成

- **判定**：简报写明的命令、镜像、工具 flag 在本机不可用或语法错误，但存在更小的等价路径能满足验收标准。
- **行动**：走最小等价路径继续。必须保留验收标准的可观察结果。偏差写入自检汇报和 changelog「已知问题」。
- **禁区**：不因此跳过验收项；不换成简报点名禁止的技术（如 ORM）。
- **T-14 实例**：旧 `docker-compose` 1.29 的 `http+docker` 不可用 → 用 Compose v2；pgloader `TABLE NAMES MATCHING` 解析失败 → `WITH data only, truncate, disable triggers, reset sequences`，导入后 `DROP sqlite_sequence`。

### D. 终态约束与工具一次性能力冲突

- **判定**：关键约束要求的**结束状态**可以满足，工具无法在单步内按字面写入。
- **行动**：允许迁移过程中的短暂偏离，任务结束时终态必须回到约束。写入已知问题。
- **T-14 实例**：pgloader 无法写入 `GENERATED ALWAYS AS IDENTITY` 列 → 导入时改为 `GENERATED BY DEFAULT`，结束后改回 `ALWAYS` 并 `setval`。

### E. 简报流程与 04 流程冲突

- **判定**：简报「完成后」要求先做清理再等验收，或要求开始下一任务。
- **行动**：以 04 为准。自检通过后停止等验收。清理只在人工回复「T-XX 验收通过」后执行。

### F. 禁止层需要方言级最小适配

- **判定**：handler / service 被标为禁止修改，但驱动或 SQL 方言更换后，不识别新错误码就无法通过验收。
- **行动**：允许不改变业务语义的适配（例如唯一约束识别增加 PostgreSQL `23505` / duplicate key）。计算公式、校验规则、状态机、接口行为保持原样。分不清时停止汇报。

### 必须停止、等待人工的情形

- 验收标准与「禁止修改 / 禁止操作」直接打架，且无法归入 F。
- 需要改锁定项，且该改动不是本任务目标。
- 简报目标、约束、验收互相矛盾到无法归入 A–F。
- 返工中发现简报本身有误。

停止时只汇报：冲突点、归入哪一类失败、建议的简报改法。不边做边改 05 简报。

## 验收通过后的清理动作（人工回复「T-XX 验收通过」后执行）
1. 在 `06-changelog.md` **顶部**追加记录：`日期 ｜ 任务ID：名称 ｜ 改动文件 ｜ 验收结果 ｜ 已知问题 ｜ 契约变更（如有）`。
2. 从 `05-roadmap.md` **删除**该任务的概览行和简报块（两者同时删除，不保留「已完成」状态）。
3. 若该任务原本有依赖它的后续任务，清理后续任务「依赖」列中对它的引用；依赖列清空时写 `—`。
4. 若执行中产生了未排期的新想法，写入 `07-todos.md`，不回填 05。
5. 若涉及数据结构、接口或技术栈变更，同步更新 `02-data-model.md`、`03-api-contract.md` 或 `01-architecture.md`。
6. 提交代码：
      git add -A
      git commit -m "feat: T-XX <任务名>"
      git push
   不打 tag。无推送权限时降级为只执行 `git add -A && git commit`，并在汇报中说明「已本地提交，未推送」。
7. 汇报：清理结果、changelog 条目、commit hash、05 中下一个待执行任务 ID。人工已要求不开始下一任务时，只点名 ID，不启动执行。

## 验收未通过时的动作
- 人工指出问题，AI 在原任务上返工，不删除简报，不进入下一个任务。
- 返工完成后重新自检并汇报，等待再次验收。
- 返工中若发现简报本身有误，先汇报，由人工修改简报后再继续，不得边做边改简报。

## 文档维护规则
- **单一事实来源**：任何信息只在一个文件定义，其他文件引用不复制。
- **AGENTS.md 保持短小**（50–150 行量级），只做索引与核心规则；新增细节写入对应子文件。
- **05 只保留未完成任务**。任务完成后，概览行与简报块必须同时删除，不得以「已完成」状态留存。历史记录只在 06 中保留一行摘要。
- **06 只增不改**，最新记录在最上方。超过约 300 行时按年归档到 `docs/archive/changelog-YYYY.md`。
- **07 中的事项**一旦确认要做，移入 05 成为任务并从 07 删除，避免两处重复。
- 新增文档文件时，必须同步更新 `AGENTS.md` 的文档索引表。

## 任务简报格式（05 中每个任务块统一使用）
- **目标**：一两句话。若目标会改锁定项，第一句写明改哪份锁定文档（01 / 02 / 03）。
- **范围边界**：允许修改 / 禁止修改 / 禁止操作。目标涉及的锁定文档必须列入允许修改。禁止项写「层 + 语义」（如 service 计算逻辑），避免笼统禁止整个文件，以便 F 类方言适配。
- **关键约束**：3–5 条硬性终态。写结束状态与禁区，少写易过时的工具 flag。
- **验收标准**：逐条可观察、可执行。
- **完成后**：停止等待验收。清理只在人工「T-XX 验收通过」后按 04 执行。
